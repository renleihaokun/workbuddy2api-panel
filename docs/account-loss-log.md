# 掉号台账（账号损失记录）

> **文档性质**：运行台账 + 事后复盘**快照**。只记录「哪一天掉了几个号、上游怎么说的、我方证据是什么、怎么处置的」。
> **以什么为准**：处置口径与状态机以 [refresh-token-lifecycle.md](refresh-token-lifecycle.md) 和代码为准；本页不重复实现细节，过期结论也不会改写历史。
> **时间口径**：除特别标注外均为**北京时间（UTC+8）**。服务器 journal 用 UTC 记时、日志正文用本机时区，引用时已换算。
> **脱敏**：不记录真实 UID / 昵称 / 邮箱 / 服务器地址。账号统一编号为 `CN-1`…`CN-n`，编号与真实账号的对应关系只留在运维侧，不进入仓库。
> **更新方式**：每次确认批量「待重登」后追加一节，不覆盖历史；无法证实的部分显式标注「未确认」，不补写成结论。

## 2026-11-26 · 傍晚集中掉 5 个号

### 现象

- 5 个账号在 **18:54 – 20:39** 之间陆续被判 `session_dead`，面板红标「待重登」。首个被判死的是 18:54，最后一个是 20:39，中间并非同时失效。
- 每个号失效的顺序都是：chat 请求先拿到 **HTML 401**（`openresty` + `Powered by apisix` 的 `401 Authorization Required` 页面，**没有**业务信封），进入 401 求证后再从 refresh 端点拿到应用层拒绝：

```
{"code":12153,"msg":"12153:refresh token failed:idsvc token: invalid_grant: refresh token revoked"}
```

- 这 5 个号签发的 access token 名义上都还在有效期内（最早 12-20，其余 12-23），但上游已经开始拒收。

### 判定与证据

1. **不是我方刷新把一次性 RT 用重了**：这 5 个号的 refreshToken 与 11-25 **23:09** 的 `auths` 快照逐字节一致（该快照已包含 11-25 22:00–22:48 那轮保活刷新），即此后我方再没动过它们的 RT；同时段日志里没有任何一次主动刷新 / 保活动作。
2. **不是有人在别处拿这些号在跑**：当日上游扣减 = 我方账单 − 当日签到增量，逐个号都能对上，没有第三方消耗。
3. 综合以上，判定为**上游把整条会话（AT + RT 链）作废**。只有这一类能同时解释「AT 未到期却被网关层拒」与「RT 报 revoked」。
4. **边界**：从我们这一侧无法区分「风控清理」与「别处登录导致会话被替换」。若同一批号曾在其他客户端登录过，两种解释都成立，本页不选边。

### 处置

| 去向 | 数量 | 说明 |
|---|---|---|
| 就地重登恢复 | 2 | 新 AT 到期 12-24，已回池 |
| 删除 | 2 | 来源为购买与借用，判断不值得再养 |
| 待重登 | 1 | 绑定手机在亲属名下，次日处理；期间保持禁用 |

### 附带观察

- 当天 `soft_rate` 事件从过去几天的 0～1 次跳到 **21 次**，并伴随 `6004 model rate limit` 的模型级锁 —— 上游侧同期在收紧。
- 5 个里 4 个是手机号打码昵称的账号（购买 / 借用来源），自有账号全部存活。样本太小，只能当**弱信号**。
- 死号当天被保号任务持续打：journal 可见范围内全天 **205 次** HTML 401，绝大多数来自这 5 个号（`schedule.include_disabled_in_tasks=true` 会让保号任务继续戳已死的号）。

### 未确认

- **发布与掉号的时间重叠未验证**：当天 18:34 与 18:56 各有一次发布（1.28.0），第一例掉号在 18:54，时间上贴着。重启本身不会吊销上游令牌，但「1.28.0 是否改了出站头 / 账务路径」没有比对过。下次复盘先拉这两个版本的差异，再谈归因。

## 2026-11-25 · 并发探活修复上线后发现掉号

### 现象

- 当天 **16:58 / 18:54 / 20:43** 三次发布（1.25.0 → 1.26.0 → 1.26.1），操作者口径是修复「并发探活」缺陷。
- 上线后清点，**6 个号掉线**（操作者记录，非本页推断）。
- 当晚 22:00 起保活按账号抖动窗口依次刷新了剩余账号的 RT —— 文件写入时刻在 22:00–22:48 之间分散，说明当时保活链路本身是正常的。

### 可证 / 不可证

| 项 | 状态 | 依据 |
|---|---|---|
| 当天账号数 24 → 20 | 可证 | 08:55 的 `state.json` 备份里 24 个号全为可用；当日起点已是 20 个 |
| 23:09 做过一次删除（含 `auths` 备份） | 可证 | `auths.bak-delete-*` 备份目录与其时间戳 |
| 6 个号的确切判词与失效时刻 | **不可证** | journal 只从 11-25 23:25 起有记录，早于此的现场已滚掉 |
| 6 = 4 删除 + 2 就地重登 | **推断** | 按当前账号差集推的；重登不换 UID，没有独立痕迹 |
| 掉号由这次修复引起 | **不能证实** | 另有两个后来被删的号最后一次接到请求是 15:26 / 15:28（早于当天第一次发布），但「没接到请求」既可能是已死也可能是没被选号器挑中，无法区分 |

### 教训

- 排查窗口短于一天时，改动前后的现场很容易被 journal 滚掉。**动账号相关代码前先导一份 `auths/` + `state.json`，并记下当时的禁用数与判词**，比事后从残片里反推便宜得多。

## 两次事件的共性

- 症状一致：先 HTML 401（网关层），求证后拿到应用层 12153；AT 都还没到期。
- 都不是「我方并发刷新把一次性 RT 用重了」那种自伤（至少 11-26 这次有指纹证据排除）。
- 共同的可疑放大器是**出口**：整池挂在同一个机房 IP 上，选号策略、并发上限都不是这个维度的变量。社区同类项目的共识也是「反代本身 + 机房出口」排在最前，用量反而有争议。

## 已落地的防护改进（1.29.0-panel）

1. **批量判死闸门**：`pool.batch_dead_threshold`（默认 `3`）/ `pool.batch_dead_window`（默认 `10m`）触发时自动暂停全部定时后台调度并告警，面板可通过 `POST /panel/api/pool/resume-gate` 恢复。
2. **台账自动化**：`data/account-loss.jsonl`（append-only，0600 权限）在首次确认 `rt_dead` / `session_dead` / `banned` / `batch_gate_tripped` 时落盘脱敏时间、UID 前缀、判词、RT sha256 指纹与 auth 文件 mtime。
3. **修复抖动 45× 重放**：`RunStreakBonusNow()` 改为按账号随 `shouldFire()` 串行执行一次（不再在 45 分钟窗口内每分钟重放全部 CN 账号），并将 `travel`、`blackcat` 纳入抖动。
4. **清除遥测指纹与降噪**：清除所有出站 `wb2api-*` / `wb2api 自动化` 字面量，增加 `schedule.keepalive_renew_before`（默认 `168h`）、`upstream.legacy_catalog_probe`（默认 `false`）与 refresh 429 全局保护性暂停。

## 判定口径速查

| 现场 | 归类 | 处置 |
|---|---|---|
| `12153 … invalid_grant: refresh token revoked` | RT 被上游作废 | 只能重登；AT 若仍可用可短暂续命 |
| `12153 … Offline user session not found` / `refresh token is invalid` | 会话注销 | 同上 |
| HTML 401（`openresty` / `apisix`，无信封） | 网关层拦截 | 先求证，不要直接判死 |
| `429` / `6004` / `6000` | 限流 | 退避，不升级为禁用 |
| `11140` + `request illegal` | 账号级封禁 | 重登无效，只能申诉 |

完整状态机见 [refresh-token-lifecycle.md](refresh-token-lifecycle.md)。
